3. Geometry partition coverage (authoritative PostGIS measurement)
------------------------------------------------------------------

Boundary: campaigns/berlin_recording_services/geography/berlin-boundary.geojson
  digest   sha256:d67bbca795b0a3f0b5741ba8609222e35cb81d3402df03fc403409e666ea0b9a
  geometry MultiPolygon, 4 parts, ring point counts 9626 (+7-point hole), 7, 6, 18

Partitioning: exact axis-aligned half-plane clipping (Sutherland-Hodgman), recursive on the
longer extent, seam vertices added, original vertices preserved.

Result: 5 partitions with ring point counts [4831, 4798, 6, 5, 17].
Every partition is at or below the 5000-point Overpass limit.
Exactly one partition declares one 6-point interior hole as an excluded_holes
over-approximation.

Measured with PostGIS geography casts, comparing the union of the 5 partition polygons with
the original boundary over the same SRID:

  boundary area .............. 891 119 585.67 m2
  missing area (boundary not covered by partitions) ... 0.000072 m2
  extra area (covered but not boundary) .............. 574.0272 m2
  covers_all_except_declared_hole .................... true

Interpretation, stated plainly:
  - No real area of Berlin is dropped. The 0.000072 m2 residue is floating-point noise at
    the clip seams, not a lost region.
  - The 574 m2 surplus is exactly the declared interior hole that no single Overpass query
    can express. It is declared in the published partition record, not silently included,
    so a consumer can see the over-approximation.
  - The query will therefore return the full city plus at most one small interior hole's
    worth of extra candidates. It cannot lose part of the city.

This replaced an earlier vertex-window split, which was measured to lose 0.02% of the
boundary (0.117906 vs 0.117926) because window chords close across the interior and query
a different region. That approach was removed rather than patched.

5. Source-record mapping behaviour proven by test
-------------------------------------------------

  - A seam duplicate (the same (elementType, osmId) returned by two adjacent partitions) is
    mapped once. Covered by test_seam_duplicate_element_identity_is_mapped_once.
  - An element that cannot be represented is skipped and its source_record_id is recorded
    on the mapping action, so the partial result is visible instead of the whole batch
    being discarded. The unrepresentable ids are included in the canonical mapping action
    payload and therefore in the durable result digest, so a partial fetch cannot later be
    replayed as complete coverage.
  - A batch in which every element is unrepresentable fails explicitly with
    PIPELINE_SOURCE_RECORD_ALL_ELEMENTS_UNREPRESENTABLE rather than succeeding empty.


6. Known latently broken code found and fixed during this run
-------------------------------------------------------------

  - campaign_runs._osm_discovery_work returned a tuple while annotated -> WorkUnitSpec, and
    its caller extends a list. mypy caught it; the annotation was corrected.
  - The partition loop in osm_query_spec used lambdas closing over the loop variable `cut`
    (ruff B023). Replaced with _below/_above predicate factories binding the value.
  - _BoundaryShape parameter annotations rejected the numeric rings callers pass; annotated
    for the coordinate sequences actually supplied.
  - test_campaign_run_service asserted a fixed initial_work count of 2, which became wrong
    once the OSM binding yields one unit per partition. It now derives the expected count
    and asserts per-binding contracts (osm-overpass-result@1, capability osm_query).
