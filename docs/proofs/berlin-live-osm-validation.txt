1. Boundary hole exclusion (change + regression proof)
------------------------------------------------------

Change: `boundary_contains` in collection_contracts/osm_query_spec.py applies the exact
original campaign boundary after acquisition, because an Overpass `poly` filter carries one
ring and cannot express interior holes. `_boundary_admitted_osm_elements` in
pipeline_advancement.py drops excluded elements and records their identities on
`SourceRecordMappingAction.excluded_by_boundary_record_ids`, which is part of the canonical
action payload and therefore of the durable result digest.

Failure semantics: when every element in a result falls inside a hole, the transition is
BLOCKed with PIPELINE_SOURCE_RECORD_ALL_ELEMENTS_OUTSIDE_BOUNDARY and zero mapping actions.
It never proceeds with an empty batch.

Regression tests (all executed, all passing):
  packages/collection_application/tests/test_osm_boundary_hole_filter.py   7 passed
  packages/collection_application/tests/test_osm_discovery_integration.py 11 passed
    - test_elements_inside_a_boundary_hole_never_reach_intake
        plan.disposition is BLOCK, source_record_mapping_actions == (),
        blocker code PIPELINE_SOURCE_RECORD_ALL_ELEMENTS_OUTSIDE_BOUNDARY,
        sourceRecordCount 3
    - test_partial_hole_exclusion_drops_the_hole_element_and_keeps_the_rest
    - test_elements_outside_a_boundary_hole_still_reach_intake

Defect found while proving this: the first version of the predicate unpacked rings as
(lon, lat) while `_raw_ring` yields (lat, lon), so containment returned False for every
point. It was caught by the test asserting a point outside the hole is admitted and fixed
in the predicate, not in the test.

3. Two real defects found by running against the live endpoint
--------------------------------------------------------------

3.1 Overpass rejected every generated query with HTTP 400.

  Server error text: `Invalid regular expression: "^(?:recording_studio)$"`.
  Cause: connectors/osm_overpass/query.py emitted a non-capturing group `(?:...)`.
  Overpass evaluates tag filters with POSIX extended regular expressions, which have no
  non-capturing group syntax.
  Fix: emit `^(recording_studio)$`. Same semantics, accepted by the server.
  Test updated (connectors/osm_overpass/tests/test_query.py now also asserts that `(?:`
  never appears). connectors/osm_overpass/tests: 28 passed.

  Note: the pre-existing test asserted the broken form, so this defect was locked in by a
  test that had never been validated against the real endpoint.

3.2 Source-record intake rejected its own batches.

  The adapter `_source_record_as_observations` rebuilt the generic batch but inherited
  `content_digest` from the source-record batch. Those are different canonical contents, so
  `verify_observation_batch` failed with "observation batch digest does not match canonical
  content" and intake could not persist anything.
  Fix: `seal_observation_batch(payload)` computes the digest from the rebuilt payload. The
  adapter still manufactures no HTML extracted-record digest and no manual-import lineage.

3.3 Replay was not identity-stable.

  `materialize_source_record_observations` defaulted `observed_at_utc` to `datetime.now()`.
  Two mappings of byte-identical evidence therefore produced different evidence digests and
  two different candidates. Measured before the fix: replaying the same result created a
  second candidate row with a different id and a different snapshot_digest.
  Pinning `observed_at_utc` to the source's own observation time reproduced the same
  candidate id (`1226bff8-247e-5349-8454-be37eb078bc6`) on two consecutive runs, with
  candidates/revisions/cases/quality all staying at 1.
  The default remains wall-clock in the worker; callers that need replay identity must pass
  the source timestamp. This is a caller contract, and is not yet enforced by the worker.


4. Website-less businesses survive, and nothing is manufactured
---------------------------------------------------------------

The acquired element carries `contact:website` but no `website` tag. The campaign projection
maps the `website` tag, so the mapper has no value for it and emits `NOT_OBSERVED`.

  website.state = not_observed, value = null, evidence = null
  display_name.state = observed, value "nb film"
  email.state = not_observed, phone.state = not_observed
  issues = []

The element still produced a candidate and a review case. Nothing was invented: no website
URL, no empty string, no `ABSENT_IN_SOURCE`. Covered by
apps/processing_worker/tests/test_source_record_mapping_worker.py::
test_absent_field_is_not_observed_never_confirmed_absent (17 worker tests pass).

A separate question worth recording, not answered here: the element does publish a website
under `contact:website`. The campaign projection reads `website` only, so a real website is
currently not captured. Mapping `contact:website` is a campaign/projection decision, not a
mapper bug, and was deliberately not changed in this run.

== OSM contact-namespace coverage (follow-up) ==
Problem: the campaign projected only the `website`/`phone`/`email` tags. OSM node
871572117 publishes its site and phone only as `contact:website` / `contact:phone`, so a
real published website was recorded NOT_OBSERVED. That is lost recall, not a mapper bug.

Decision: aliases are source tags feeding one existing typed target, not new targets.
`SourceFieldProjection.source_aliases` (additive) carries them; the immutable campaign
binding stays the single owner of the decision.
  website <- website, contact:website
  phone   <- phone,   contact:phone
  email   <- email,   contact:email
All three source tags are permitted by `osm_berlin_studios_policy.yaml` allowed_fields.

Semantics implemented:
  - every authorized tag yields its own evidence pointer /tags/<tag>;
  - identical normalized values collapse to one observation;
  - distinct conflicting values are all kept for review, never overwritten;
  - OBSERVED when at least one authorized tag carries a value;
  - NOT_OBSERVED only when no authorized tag carries one; never ABSENT_IN_SOURCE.

Measured on the real acquired node (end-to-end through the real campaign bundle):
  profile fieldAliases = {email:[email,contact:email],
                          phone:[phone,contact:phone],
                          website:[website,contact:website]}
  website -> observed  http://www.nbfilm.de   evidence /tags/contact:website
  phone   -> observed  +49 30 31169672        evidence /tags/contact:phone
  email   -> not_observed (genuinely absent; no ABSENT_IN_SOURCE anywhere)
  plan digest and mapped batch digest identical across two replays.

Website-less business regression: with `contact:website` removed, website stays
not_observed while display_name stays observed; the record still maps and intakes.
